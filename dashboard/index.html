An agent that runs procure-to-pay, and checks its own work.

A successful-looking write is not a completed write. HTTP 200 means the server accepted the request, not that the stored document says what you believe it says. So every write here is followed by a read, and a mismatch has its own exception type that is never swallowed.

What the evaluation found

The harness was not a scoreboard. It found two genuine product bugs, three scenarios of mine that were wrong, and one that asserted behaviour the test double could not have.

A rejected approval was never recorded as one

The driver checked “has this been rejected?” after every node, so a pre-set rejection escalated the run immediately after extract — before policy_check ran. The trace then read “no approval required” for an order that had just been refused.

…and the fix for it silently did nothing

fn is self.n_approval_gate is never true: Python builds a new bound-method object on every attribute access, so identity comparison always fails. The run fell through to submit_purchase_order, which refused it — the defence-in-depth guard caught the consequence while the cause went unnoticed. == fixed it.

Policy is a document, not code

No threshold is in the source. The agent retrieves these with embeddings and cites the rule id on every decision. Change a number in the document and the next run behaves differently — no code change, no redeploy.

R3 and R4 combine their two limits differently on purpose. Price takes the tighter of 5% and ₹500; quantity takes the greater of 2% and 1 unit. 5% of a ₹28 pair of gloves costs more to investigate than to pay, while 2% of 10 units would make every single-unit discrepancy an exception. Both directions are tested.
